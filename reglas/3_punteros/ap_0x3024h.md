(ap_0x3024h)=
# Antipatrón AP-0x3024h: Asignación múltiple a malloc en bucle sin liberación ante fallos parciales

:::{admonition} Regla de Estilo Asociada: 0x3001h
:class: tip
La transgresión descripta en este antipatrón se encuentra normada por la
**[0x3001h: Siempre verificá la asignación exitosa de memoria dinámica](0x3001h.md)**.
:::

:::{admonition} Diagnóstico de Antipatrón
:class: warning
Código de auditoría: `AP-0x3024h` | Categoría: Punteros y Gestión de Memoria (0x30XX)
:::

## Síntoma en el código del estudiante

En una reserva por filas, el chequeo de `NULL` dentro del bucle no libera lo ya
asignado:

```c
for (int i = 0; i < n; i++) {
    mat[i] = malloc(m * sizeof(int));
    if (mat[i] == NULL) {
        return NULL;
    }
}
```

Si falla la fila `k`, las filas `0..k-1` quedan sin dueño.

## Diagnóstico

### Mecanismo del defecto

Una matriz dinámica se construye con **una reserva por fila**. El bucle avanza
asignando bloques independientes. Si una reserva intermedia falla, el retorno
inmediato abandona el bucle, pero las reservas anteriores siguen vivas en el
heap y ya nadie conserva sus punteros: son **fugas irrecuperables**.

La cantidad de memoria perdida crece con la cantidad de filas asignadas antes
del fallo. En un programa que reintenta la operación, cada intento fallido
filtra otro bloque completo. Peor: si el fallo se debió a falta de memoria, la
fuga agrava la escasez.

### Consecuencia observable

- Fuga de memoria que no se manifiesta con pocos elementos.
- Degradación progresiva del proceso hasta agotar la memoria.
- Valgrind o LeakSanitizer reportan bloques "definitely lost" cuya pila de
  asignación señala el `malloc` del bucle.

## Fundamento en el estándar C11

- C11 §7.22.3.3: cada bloque reservado con `malloc`/`calloc`/`realloc` debe
  liberarse con `free`; no hay recolección automática de basura.
- C11 §7.22.3p1: ante el fallo, `malloc` retorna `NULL` y no altera los bloques
  previos.
- La regla 0x300Fh complementa: la liberación de recursos anidados se hace en
  orden inverso al de asignación (de la última fila a la primera).

## Corrección idiomática

### ❌ Código con el antipatrón

```c
int **crear_matriz(size_t n, size_t m)
{
    int **mat = malloc(n * sizeof(*mat));
    if (mat == NULL) {
        return NULL;
    }
    for (size_t i = 0; i < n; i++) {
        mat[i] = malloc(m * sizeof(*mat[i]));
        if (mat[i] == NULL) {
            return NULL;   /* fuga de mat[0..i-1] y de mat */
        }
    }
    return mat;
}
```

### ✅ Código refactorizado — limpieza en orden inverso

```c
int **crear_matriz(size_t n, size_t m)
{
    int **mat = malloc(n * sizeof(*mat));
    if (mat == NULL) {
        return NULL;
    }

    for (size_t i = 0; i < n; i++) {
        mat[i] = malloc(m * sizeof(*mat[i]));
        if (mat[i] == NULL) {
            for (size_t j = 0; j < i; j++) {
                free(mat[j]);
            }
            free(mat);
            return NULL;
        }
    }
    return mat;
}
```

La liberación recorre las filas ya asignadas (`j < i`) y luego libera el arreglo
de punteros; ese orden inverso es el que exige la regla 0x300Fh.

### ✅ Alternativa — un único bloque contiguo

```c
int *datos = malloc(n * m * sizeof(*datos));
```

Con un solo `malloc` no hay fallo parcial posible; simplifica la propiedad y es
preferible cuando no hace falta que las filas sean intercambiables.

### ⚠️ Casos límite

- Si `n == 0`, `malloc(0)` puede devolver `NULL` sin ser un error real.
- La liberación posterior también debe ser simétrica: primero las filas y al
  final el arreglo de punteros.

## Errores típicos al compilar o ejecutar

```text
$ valgrind --leak-check=full ./programa
==1234==    definitely lost: 320 bytes in 40 blocks
==1234==      by 0x...: crear_matriz (programa.c:10)
```

## Checklist de verificación

- [ ] ¿Ante un fallo parcial libero todo lo asignado hasta el momento?
- [ ] ¿La liberación es en orden inverso al de asignación (regla 0x300Fh)?
- [ ] ¿Liberé también el arreglo de punteros de nivel superior?
- [ ] ¿Consideré usar un único bloque contiguo?
