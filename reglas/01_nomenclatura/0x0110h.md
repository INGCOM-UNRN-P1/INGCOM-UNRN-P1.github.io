(0x0110h)=
# 0x0110h: Los booleanos se nombran con prefijo interrogativo

:::{admonition} Categoría: Nomenclatura e identificadores (0x01XX)
:class: note
Código de regla: `0x0110h` | Soporta corrección automática: **No**

:::
<!-- {admonition} Categoría: Nomenclatura e identificadores (0x01XX) -->

## Enunciado normativo

> Las variables y funciones de tipo `bool` **DEBEN** nombrarse de modo que se
> lean como una pregunta cuya respuesta es sí o no, usando prefijos como
> `es_`, `esta_`, `tiene_`, `puede_`, `hay_` o `debe_`.

## ¿Por qué existe esta regla?

### El problema

Un booleano llamado `dato` o `flag` no indica **qué** afirma sobre el mundo.
El lector debe ir a buscarlo en la asignación para saber si `dato` verdadero
significa "hay datos" o "los datos son válidos". Con un nombre interrogativo,
la condición se lee como una frase: `if (hay_datos)` se entiende sin contexto.

La convención también distingue visualmente los booleanos de los enteros, que
en C comparten representación. Un `int` llamado `activo` es ambiguo; un
`bool es_activo` no.

### Consecuencias de violarla

| Tipo de consecuencia | Efecto concreto |
| :--- | :--- |
| Lectura | La condición exige recordar qué afirma la variable. |
| Bug lógico | Invertir la polaridad es fácil cuando el nombre no la expresa. |
| Consistencia | Unos booleanos usan `flag`, otros `ok`, otros `estado`, sin criterio. |
| Revisión | El docente no puede evaluar la condición de un vistazo. |

### Fundamento en la cátedra

Extiende {ref}`0x0101h` al caso particular de los booleanos y se articula con
{ref}`0x1005h`, que exige comparar los booleanos contra `true`/`false` y no
contra números, y con {ref}`0x301Ah`, que exige usar el `bool` estándar.

## Alcance y excepciones

Aplica a variables, parámetros y funciones que devuelven `bool`. No aplica a
campos de bits ni a códigos de estado numéricos, que tienen su propia
convención ({ref}`0x2007h`).

## Ejemplos exhaustivos

### ❌ Contraejemplo 1 — Nombre sin pregunta

``` c
bool dato = leer_entrada();

if (dato) {
    procesar();
}
```
<!-- c -->

Por qué falla: no se sabe si `dato` significa "la lectura tuvo éxito", "hay
datos" o "los datos son válidos". La condición es incomprensible sin mirar la
llamada.

### ❌ Contraejemplo 2 — Polaridad oculta

``` c
bool error = detectar_fallo();

if (!error) {
    continuar();    /* doble negación: ¿no hay error? */
}
```
<!-- c -->

Por qué falla: el nombre afirma "error" y la condición niega; el lector debe
hacer el giro mental en cada uso (ver {ref}`0x0111h`).

### ✅ Ejemplo conforme 1 — Prefijo interrogativo

``` c
bool hay_datos = leer_entrada();

if (hay_datos) {
    procesar();
}
```
<!-- c -->

La condición se lee como una pregunta: "¿hay datos?".

### ✅ Ejemplo conforme 2 — Función de predicado

```{code-block} c
:linenos:
static bool es_par(int numero)
{
    return numero % 2 == 0;
}

static bool tiene_permiso(const usuario_t *u, permisos_t p)
{
    return (u->permisos & p) != 0;
}

```
<!-- {code-block} c -->

``` c
if (es_par(valor) && tiene_permiso(usuario, ESCRITURA)) {
    /* ... */
}
```
<!-- c -->

Las llamadas se leen como frases afirmativas; el prefijo `es_`/`tiene_`
identifica el rol booleano de inmediato.

### ⚠️ Casos límite

- **Booleanos de biblioteca:** funciones estándar como `feof` no siguen la
  convención, pero su significado ya está fijado por el estándar.
- **Nombres de dominio:** si el dominio ya tiene una palabra clara ("vigente",
  "caducado"), se admite como excepción documentada.
- **Negativos:** prefiera siempre la forma positiva; `es_valido` antes que
  `no_es_invalido` ({ref}`0x0111h`).

## Cómo detectarla

| Herramienta | Comando | Señal |
| :--- | :--- | :--- |
| Revisión manual | — | Variables `bool` sin prefijo interrogativo. |
| `gaff` | `gaff check archivo.c` | Regla `0x0101h` (nombres descriptivos) y `0x301Ah` (`bool` estándar). |

## Checklist de autocontrol

- [ ] ¿El nombre del booleano se lee como una pregunta?
- [ ] ¿La polaridad es positiva?
- [ ] ¿Distingo el booleano de un entero por el nombre?
- [ ] ¿El tipo es `bool` de `<stdbool.h>`?
