(0x3018h)=
# 0x3018h: Inicialización idiomática de agregados con {0} en lugar de memset inmediato

:::{admonition} Categoría: Memoria, punteros y tipos (0x30XX)
:class: note
Código de regla: `0x3018h` | Soporta corrección automática: **No**

:::
<!-- {admonition} Categoría: Memoria, punteros y tipos (0x30XX) -->

## Enunciado normativo

> Las variables locales de tipo `struct` o arreglo que deban quedar en cero
> **DEBEN** inicializarse en su declaración con `= {0}`. **NO DEBE** declararse
> la variable sin inicializar y emitir a continuación un `memset` para llevarla
> a cero.

## ¿Por qué existe esta regla?

### El problema

Declarar una variable y luego inicializarla con `memset` separa dos hechos que
deberían ser uno: la variable existe, y existe sin un valor definido durante un
instante. En ese intervalo, cualquier acceso accidental lee basura. Además, el
`memset` puede escribirse mal (ver {ref}`0x3016h`) o puede olvidarse por
completo
en un camino de error.

La inicialización en la declaración elimina el estado intermedio: no hay ningún
punto del código donde la variable sea observable sin un valor conocido. Es más
corta, más difícil de omitir y el compilador la entiende como parte de la
declaración.

### Consecuencias de violarla

| Tipo de consecuencia | Efecto concreto |
| :--- | :--- |
| Estado transitorio | Entre la declaración y el `memset` la variable contiene basura. |
| Bug silencioso | Si el `memset` se omite en una rama, los campos quedan sin inicializar. |
| Ruido | Dos sentencias donde alcanza una; más código que revisar. |
| Errores de argumentos | El `memset` mal escrito no inicializa y nadie lo nota. |

### Fundamento en el estándar y en la cátedra

C11 §6.7.9 permite inicializar agregados con una lista entre llaves; si se da
menos inicializadores que elementos, el resto se inicializa a cero. Por eso
`{0}` lleva todos los campos a cero. La cátedra prefiere esta forma sobre
`memset` por claridad y por la regla de inicialización de {ref}`0x7001h`. El
`memset` queda para rellenar con bytes distintos de cero o para regiones ya
existentes.

## Alcance y excepciones

Aplica a agregados locales (arreglos y structs) que deban quedar en cero.
**No** aplica a memoria del *heap*: un bloque reservado con `malloc` no puede
inicializarse en la declaración; allí se usa `calloc` o un `memset` posterior
con
el orden correcto. Tampoco prohíbe `memset` para rellenar con un patrón distinto
de cero (`0xFF`, `'A'`).

## Ejemplos exhaustivos

### ❌ Contraejemplo 1 — Declarar y limpiar con `memset`

``` c
struct punto_t punto;
memset(&punto, 0, sizeof(punto));
punto.x = 1.0;
```
<!-- c -->

Por qué falla: entre la declaración y el `memset`, `punto` contiene basura; si
una refactorización mueve código entre esas líneas, aparece un bug por dato sin
inicializar. La forma idiomática lo expresa en una sola línea.

### ❌ Contraejemplo 2 — Arreglo del que se olvida el `memset`

```{code-block} c
:linenos:
int acumuladores[10];
if (modo_especial)
{
    memset(acumuladores, 0, sizeof(acumuladores));
}
acumuladores[0] += valor;

```
<!-- {code-block} c -->

Por qué falla: el `memset` está dentro de una rama condicional, de modo que en
el camino normal los acumuladores quedan sin inicializar y la suma parte de
basura. Inicializar en la declaración elimina la posibilidad de olvidar la rama.

### ✅ Ejemplo conforme 1 — Inicialización en la declaración

``` c
struct punto_t punto = {0};
int acumuladores[10] = {0};
punto.x = 1.0;
acumuladores[0] += valor;
```
<!-- c -->

Ambas variables tienen un valor conocido desde el instante en que existen. No
hay sentencia separada que pueda omitirse y el compilador inicializa a cero
todos
los elementos no nombrados.

### ✅ Ejemplo conforme 2 — Memoria del *heap* con `calloc`

``` c
int *valores = calloc(cantidad, sizeof(*valores));
if (valores == NULL)
{
    return NULL;
}
```
<!-- c -->

Cuando la memoria viene del *heap*, `calloc` inicializa en cero y a la vez
verifica el desbordamiento del producto. Si se usara `malloc`, correspondería
`memset(valores, 0, cantidad * sizeof(*valores))` con el orden canónico y la
verificación de {ref}`0x3001h`. `{0}` no puede aplicarse a memoria reservada
dinámicamente.

### ⚠️ Casos límite

- **Inicialización parcial a un valor:** `struct punto_t p = {1.0, 2.0};` nombra
  los primeros campos y pone el resto en cero; es válido y no es "medio
  inicializado".
- **Variables estáticas:** ya están garantizadas en cero por C11 §6.7.9; `= {0}`
  es redundante pero inocuo y a veces explícito.
- **`= {0}` y el primer elemento:** en un arreglo, el `0` correponde al primer
  elemento y el resto se completa con ceros; no es un inicializador especial.
- **Structs con arreglos flexibles:** la inicialización con `{0}` no reserva el
  arreglo flexible; hay que sumar su tamaño (ver {ref}`0x300Bh`).

## Cómo detectarla

| Herramienta | Comando | Señal |
| :--- | :--- | :--- |
| `gaff` | `gaff check archivo.c` | Declaración de agregado local seguida de `memset` a cero. |
| `gcc` / `clang` | `gcc -Wall -Wextra -Wuninitialized -std=c11 ...` | `may be used uninitialized` si falta la inicialización. |
| Revisión manual | — | `memset(&x, 0, sizeof(x))` inmediatamente después de declarar `x`. |

## Checklist de autocontrol

- [ ] ¿Inicialicé los agregados locales en su declaración?
- [ ] ¿Usé `= {0}` y no un `memset` inmediato?
- [ ] ¿La memoria del *heap* usa `calloc` o un `memset` bien ordenado?
- [ ] ¿El `memset` que queda rellena con un valor distinto de cero?
- [ ] ¿Evité dejar variables en cero sin inicializar entre declaración y uso?

## Reglas relacionadas

* {ref}`0x7001h` — toda variable se inicializa a un valor conocido.
* {ref}`0x3016h` — orden canónico de los argumentos de `memset`.
* {ref}`0x300Bh` — tamaño correcto en la inicialización de memoria dinámica.
* {ref}`0x301Ch` — las variables `const` se inicializan en la declaración.
