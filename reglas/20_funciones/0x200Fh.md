(0x200Fh)=
# 0x200Fh: Prohibición de paréntesis superfluos en sentencia return

:::{admonition} Categoría: Funciones, contratos y modularizacion (0x20XX)
:class: note
Código de regla: `0x200Fh` | Soporta corrección automática: **Sí**

:::
<!-- {admonition} Categoría: Funciones, contratos y modularizacion (0x20XX) -->

## Enunciado normativo

> **NO DEBEN** envolverse en paréntesis la expresión de una sentencia
> `return`. **DEBE** escribirse `return expresion;` y usar paréntesis solo
> cuando la propia expresión los necesite por precedencia.

## ¿Por qué existe esta regla?

### El problema

`return` es una palabra clave de control de flujo, no una llamada a función. Por
eso `return (x);` no invoca nada: los paréntesis son ruido sintáctico. Ese
ruido tiene dos costos. Primero, sugiere que `return` es una función, una
confusión conceptual que reaparece cuando el estudiante escribe `exit (0)` o
`sizeof (int)` con el mismo estilo. Segundo, un par de paréntesis de más
esconde la expresión real: cuanto más envuelto está el cálculo, más difícil es
leer la precedencia.

### Consecuencias de violarla

| Tipo de consecuencia | Efecto concreto |
| :--- | :--- |
| Concepto | Refuerza la idea equivocada de que `return` es una función. |
| Legibilidad | El paréntesis compite con los de la expresión y distrae. |
| Consistencia | Unos `return` con paréntesis y otros sin ellos delatan descuido. |
| Ruido diffs | El autofix reescribe líneas que no aportaban cambio semántico. |

### Fundamento en el estándar y en la cátedra

La gramática de C11 define `return` con una expresión opcional que ya admite
paréntesis como parte de la propia expresión (§6.8.6.4). La norma no prohíbe
`return (x);`: es perfectamente válido. La cátedra lo marca por estilo, en
línea con {ref}`0x301Bh` (casts innecesarios) y con la idea de que la forma
sintáctica debe reflejar la semántica. Tiene corrección automática porque la
transformación no cambia el significado.

## Alcance y excepciones

Aplica a la expresión completa. **No** se eliminan los paréntesis internos que
la expresión necesita:

- `return (a + b) * c;` → los paréntesis son de la multiplicación.
- `return condicion ? a : b;` → sin paréntesis extra.
- `return (struct punto_t){x, y};` → los paréntesis son parte del compuesto
  literal, no del `return`.

La regla solo quita el par que envuelve **toda** la expresión.

## Ejemplos exhaustivos

### ❌ Contraejemplo 1 — Paréntesis envolvente simple

``` c
int suma(int a, int b)
{
    return (a + b);
}
```
<!-- c -->

Por qué falla: el paréntesis exterior no cumple ninguna función. La expresión
`a + b` es la misma con o sin él, y sugiere erróneamente que `return` es una
llamada.

### ❌ Contraejemplo 2 — Paréntesis en cada rama

```{code-block} c
:linenos:
int maximo(int a, int b)
{
    if (a > b) {
        return (a);
    }
    return (b);
}

```
<!-- {code-block} c -->

Por qué falla: además de los paréntesis superfluos, hay dos puntos de salida
({ref}`0x200Ch`). El estilo de `return (variable);` es puro ruido y no aporta
claridad sobre cuál es el mayor.

### ✅ Ejemplo conforme 1 — Retorno directo

``` c
int suma(int a, int b)
{
    return a + b;
}
```
<!-- c -->

La expresión se lee tal cual es. El estilo coincide con el de las funciones de
la biblioteca estándar.

### ✅ Ejemplo conforme 2 — Paréntesis solo donde la precedencia lo exige

```{code-block} c
:linenos:
int escala(int a, int b, int c)
{
    return (a + b) * c;
}

double mitad(int x)
{
    return (double)x / 2.0;
}

```
<!-- {code-block} c -->

En el primer caso el paréntesis define la precedencia de la suma; en el
segundo, el cast `(double)` es necesario. Ninguno es el par envolvente que la
regla prohíbe.

### ⚠️ Casos límite

- **Literal compuesto:** `return (struct punto_t){1, 2};` conserva los
  paréntesis porque pertenecen al compuesto literal.
- **Macros:** `return CUADRADO(x);` no lleva paréntesis extra; la macro debe
  proteger sus parámetros ({ref}`0x500Ah`).
- **Operador coma:** `return (a, b);` sí necesita el par para no cambiar la
  gramática; es una excepción legítima, aunque el operador coma en `return` es
  un olor y conviene evitarlo.

## Cómo detectarla

| Herramienta | Comando | Señal |
| :--- | :--- | :--- |
| `gaff` | `gaff check archivo.c` | `return (` que envuelve toda la expresión. |
| `gaff` | `gaff fix archivo.c` | Elimina el par superfluo. |
| `grep` | `grep -nE "return \(.*\);" archivo.c` | Revisar manualmente cuáles son envolventes. |

## Checklist de autocontrol

- [ ] ¿Mis `return` escriben la expresión directamente?
- [ ] ¿Los paréntesis que quedan son necesarios por precedencia?
- [ ] ¿Evité tratar `return`, `exit` o `sizeof` como funciones?
- [ ] ¿El estilo es uniforme en todo el archivo?

## Reglas relacionadas

* {ref}`0x301Bh` — el mismo criterio aplica a los casts innecesarios.
* {ref}`0x200Ch` — el retorno se concentra; esta regla limpia su forma.
* {ref}`0x0003h` — el espaciado alrededor de operadores también cuida la forma.
* {ref}`0x2003h` — el valor documentado debe coincidir con la expresión
  devuelta.
